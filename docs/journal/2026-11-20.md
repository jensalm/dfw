# macOS windows

Mega's macOS app drove this (mega's journal of the same day carries the product side). Exercised on macOS 26.6, arm64, from bundles with `LSUIElement`; the spike's evidence is what `examples/dfw-example-macos` now reproduces.

**On macOS 26, Control Center draws every status item**, the app's own included, so `CGWindowListCopyWindowInfo` filtered by the daemon's pid finds no window even when the item shows. Count Control Center's layer-25 windows before and after the daemon starts instead. That is how the next point was found.

**A script as `CFBundleExecutable` hides the status item.** With the Go binary as the executable, the item appears; with a script that `exec`s the binary at once, or through a login shell, the process runs, `systray`'s `onReady` runs, and nothing shows. Not understood beyond that; `building.md` says it as a rule for products.

**Why the activation is retried.** `activateIgnoringOtherApps:` once the loop turns brings the window in front when the window is started by any process while another app is frontmost. Started from a status item's menu, it loses the activation again, to the app that was active before the menu, as the menu closes. Jens, testing by hand, saw the window in front but the keyboard still in Finder. One more activation at 800 ms, only if not active, fixed it. Cooperative `[NSApp activate]` (macOS 14) is refused in every case: nothing yields to a process the daemon started.

**Considered and not done: spawning the window through LaunchServices** (`open -n --env DFW_DAEMON_ADDR=… App.app --args window`). It also takes the focus, but `SpawnSelf`'s exec does once the window process activates itself, and LaunchServices would lose the child handle and the environment `SpawnSelf` passes. Exec stays.

**webview_go's UI delegate is dead on arrival.** `webview.h` wraps it in `objc::autoreleased` and sets it as `UIDelegate`, which WKWebView holds weakly; read back one moment after the window opens, `UIDelegate` is `nil`. So the file chooser has never worked on macOS with the pinned webview_go, and new-window links had nothing to answer them. The first attempt here, adding a method to webview_go's `WebviewWKUIDelegate` class, failed for that reason. `DFWUIDelegate` replaces it, held by the web view through an associated object. It implements `runOpenPanel…` itself, so nothing of webview_go's delegate is lost. If a later webview_go keeps its delegate alive and gives it more methods, dfw's replaces them, so check what that delegate answers when webview_go is bumped. `TestNativeUIDelegateOutlivesTheSetup` fails with the association removed; it was run that way once to show it.

**webview_go sets the regular policy and activates only when the app is not bundled.** That is why bundled windows were accessories, and why `prepareNativeApp` sets the policy before `webview.New`.

**Quit is `performClose:` aimed at the window, not `terminate:`.** `terminate:` would `exit()` inside the run loop, before `Window` returns and saves the window state. `TestNativeMainMenuQuitClosesTheWindow` holds it.

**The native tests run in `TestMain`.** AppKit wants the main thread, which only TestMain's goroutine holds, through webview_go's `LockOSThread` in `init`. cgo is not allowed in `_test.go` files, so `newNativeHiddenWindow` and the `describeNative…` helpers live in `app_darwin.go`.

**Reopen is an Apple Event handler, not a delegate method.** systray sets its own NSApplication delegate, and `applicationShouldHandleReopen:` on it would mean patching its class. `NSAppleEventManager` takes a handler for `kAEReopenApplication` from any object. It must be installed after `finishLaunching`, which registers NSApplication's own handler for the same event and would replace an earlier one. That is why it is installed from the tray's `onReady`, through `dispatch_async` to the main queue. The handler is in `reopen_darwin.m`, because `reopen_darwin.go` exports `dfwTrayReopened` and a preamble in a file with `//export` may only declare.

Live state: the fixture's steps 1 to 7 were run; a file choice returning to the page was not. Window position is still not persisted on macOS, and `OnCloseRequest` still fails there. Mega needs neither.

# macOS quit from outside the window

From the review of `a1fc78b`. Window processes now get a Dock icon, so a Dock Quit reached `terminate:` and `exit()`. A logout or `quit app` did the same. `Window` and `Run` never returned.

**The quit Apple Event handler, not `applicationShouldTerminate:`.** `NSTerminateCancel` cancels a logout. `NSTerminateLater` needs a reply, and dfw's cleanup runs only after the run loop has ended. The handler only calls `performClose:`, the same as Cmd+Q, so a future macOS `OnCloseRequest` on `windowShouldClose:` covers both.

**Install timing is coupled to webview_go.** `dfw_install_quit_handler` runs in `applyNativeApp`. That is safe only because webview_go's constructor runs `[NSApp run]` until `applicationDidFinishLaunching:`, and `finishLaunching` is where AppKit registers its own handler. A scratch program showed that a second `[NSApp run]` does not register it again. If a webview_go bump stops running the app in its constructor, move the install into the ready dispatch, after the loop starts, as the tray does for reopen.

**`dfw_make_closable` is load-bearing.** It is not cosmetic. A titled-only window ignores `performClose:`. A scratch run showed that `windowShouldClose:` was never called. Without it, a window with no size cannot be closed by Cmd+Q, the Dock or a logout.

**Tests.** The test binary never runs `finishLaunching`, so AppKit's quit handler is never registered there. With dfw's handler removed, the test fails with 0 close requests. The binary does not exit. Both new tests were run once with their fix removed and failed. Live check: a bare `Window` binary got `NSRunningApplication terminate` and printed `Window returned` plus its deferred line, with a size and without one. With AppKit's handler, it exited 0 and printed neither.

Not verified: the real Dock menu and a real logout by hand. Also not verified: a quit while a file-chooser sheet is open. `performClose:` may refuse then, and a logout would wait on it.

Open findings from the same review, not addressed: the daemon still exits on a quit Apple Event without `OnQuit` or cleanup; tray `onExit` never runs on macOS, so the reopen handler and Stop watcher leak; `alert`, `confirm` and `prompt` do nothing on macOS; the 800 ms re-activation can take back the focus after Cmd+Tab; `OnReopen` gets no address and can open duplicate windows; the darwin `TestMain` needs a GUI session; the reopen test hangs instead of failing if the handler becomes synchronous; and the new-window scheme allowlist has no test.
